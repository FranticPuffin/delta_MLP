这份 `datapreprocess.py` 脚本的作用是**为地面探测站（DSN）调度系统生成模拟的高并发、多冲突基准数据集**。它通过数学分布随机生成了 40 台地面天线和 100 个航天器探测任务的复杂互斥关系。

以下是该数据集中所有参数及其业务含义的详细拆解：

## 一、 顶层任务参数 (Mission-level Parameters)

每个航天器任务（如 `JNO` 木星探测器或 `MIS-005` 随机任务）在 JSONL 文件中对应一行，包含以下全局属性：

| **参数名称**         | **数据类型** | **业务含义与作用**                                           |
| -------------------- | ------------ | ------------------------------------------------------------ |
| `mission_id`         | `String`     | **任务/航天器唯一标识符**。如经典任务模板中的 `"DAWN"`、`"JNO"` 或随机生成的 `"MIS-045"`。 |
| `total_requested_hr` | `Float`      | **总申请通信时长（小时）**。该航天器在这一周（168小时）内，总共需要地面站提供多少小时的跟踪服务。这是计算最终**任务满意度**的分母。 |
| `base_priority`      | `Integer`    | **基础优先级（1-5）**。静态赋予该航天器的核心等级，数字越大越重要（1:常规模拟 $\rightarrow$ 5:不可重访的紧急飞掠）。它作为整个调度周期的“优先级底色”。 |
| `priority_schedule`  | `List[Dict]` | **动态优先级时段表**。由于航天器在轨会遭遇突发事件（如飞掠或设备故障），其优先级会动态演变。该表将 168 小时切分成多段，详细定义了每个时间区间的实时优先级。 |
| `activities`         | `List[Dict]` | **活动任务序列**。该航天器在这周内需要拆分执行的具体通信/探测事件列表。 |

### `priority_schedule` 内嵌参数：

- `start_hr` / `end_hr`: 该优先级区间的开始与结束时间（单位：小时，范围 $0.0 \le t \le 168.0$）。
- `priority`: 该时段的实际优先级。脚本有 **30% 的概率**让某些时段的优先级在 `base_priority` 的基础上**提档 1~2 级**（最高封顶 5 级），以此模拟关键科学观测事件。

## 二、 活动参数 (Activity-level Parameters)

每个航天器任务旗下包含 $5 \sim 21$ 个不等的具体 `activities`（跟踪活动）。这些参数直接参与 MILP 模型中决策变量的物理约束控制：

| **参数名称**   | **数据类型** | **业务含义与作用**                                           |
| -------------- | ------------ | ------------------------------------------------------------ |
| `activity_id`  | `String`     | **活动唯一标识符**。格式为 `"{mission_id}_ACT_{序号}"`，是 MILP 模型中二进制决策变量 $x_a$ 的变量名绑定源。 |
| `d_min`        | `Float`      | **单次通信最小持续时间（小时）**。允许调度器进行动态缩减的底线时间（通常为 2~4 小时）。 |
| `d_max`        | `Float`      | **单次通信最大（期望）持续时间（小时）**。航天器本次科学下行最理想的连续跟踪时长（通常为 5~9 小时）。 |
| `setup_min`    | `Integer`    | **建链准备时间（分钟）**。**固定为 60 分钟**。天线开机、转动指向航天器并进行射频对准所需的物理耗时。 |
| `teardown_min` | `Integer`    | **关机拆除时间（分钟）**。**固定为 15 分钟**。通信结束天线重置、日志归档所需的耗时。 |
| `can_split`    | `Boolean`    | **是否允许 XOR 拆分**。脚本规定：如果期望最大时长 `d_max >= 8.0` 小时，则该任务允许被一拆为二。这为 MILP 算法提供了灵活变通的调度空间。 |
| `view_periods` | `List[Dict]` | **可选可见性窗口（几何视窗）**。航天器由于轨道几何运动，在这周内可以被哪些地面天线在哪些时间段看到。 |

## 三、 视窗参数 (View Period Parameters)

`view_periods` 数组中包含了 $1 \sim 4$ 个可选的天线窗口。**这属于典型的“1对多”多备选空间**：

- `antenna`: **指派的地面天线编号**。扩充后的天线池包含 40 台天线（`DSS-10` 到 `DSS-49`），模拟分布在全球三大深空综合体的天线阵列。
- `start_hr`: **视窗开启时间（小时）**。在一周 168 小时内随机均匀分布。
- `end_hr`: **视窗关闭时间（小时）**。等于 `start_hr` 加上一个随机生成的几何可见时长（范围为 `d_max` 到 `d_max + 6` 小时），确保视窗长度大于活动最大需求，提供滑动排班余量。

## 四、 整体数据集的设计特征与隐性约束

这份数据并非盲目随机，其中隐藏了专门用来检验调度算法（Delta-MILP）健壮性的**制造冲突机制**：

1. **资源过载（Over-subscription）**：

   低优先级任务（1级和2级）占比高达 **45%**，科学数据下行（3级）占 **30%**。大量低优先级任务在 168 小时内高频申请长达 5~9 小时的时段，使得整体需求远远超过 40 台天线总容量的 70% 阈值，从而暴露出巨大的**时空碰撞冲突**。

2. **刚性开销（Overhead Block）**：

   每个活动不论大小，都要额外吞噬 `60分钟(Setup) + 15分钟(Teardown) = 1.25小时` 的不可视硬性天线时间。算法必须在消解冲突时合并或优化这些闲置开销。

3. **多约束交织**：

   同一个活动可能有 3 个可选视窗（分别对应 DSS-12、DSS-25、DSS-40），算法必须在**多选一**的同时，确保这个航天器（`mission_id`）不会在同一时刻被两台天线重复抓取（任务级互斥）。
